## 생성 파이프라인

### 사진 → 프로필 생성 파이프라인을 FastAPI·Celery 비동기 단계(배경 제거 → 캐릭터 시트 → 레이아웃 보정)로 설계·구축

{/* ev: tynt_ai_backoffice src/api/pipelineTest.ts; tynt_ai_frontend_v2 BULK_POLLING_API_SPEC.md (6de07195a, 433abf4bd) */}

생성은 여러 단계를 거치는 비동기 작업이라 클라이언트가 진행 상태를 반복해서 조회한다. 상태 조회는 진행 화면의 SSE와 갤러리·앨범·실험실의 자산별 폴링으로 나뉘어 있었고, SSE 화면마다 재연결·연결 유지·오류 처리를 따로 구현했다. 자산별 폴링은 처리 중인 자산이 10개면 3초마다 요청 10건을 보내, 브라우저 동시 연결 한도(6~8개)와 요청마다 반복되는 인증·DB 조회가 부담이었다. {/* ev: tynt_ai_frontend_v2 docs/api/SSE_TO_POLLING_MIGRATION.md (Before 구조); BULK_POLLING_API_SPEC.md (Current Problem) */}

- 단계마다 Celery 태스크를 두고 앞 단계 결과를 다음 단계 입력으로 넘김. 배경 제거·얼굴 크롭(원본 1~2장) → 캐릭터 시트 → 캐릭터 시트·얼굴 크롭·컨셉 액션 이미지를 합친 최종 이미지 순서 {/* ev: tynt_ai_backoffice src/api/pipelineTest.ts (Step1~3 request and result types) */}
- 단계별로 따로 호출하는 관리자 API가 태스크 ID를 돌려주고 태스크 상태(PENDING·STARTED·SUCCESS·FAILURE 등)로 완료를 확인해, 백오피스에서 단계 하나만 실행·점검 가능 {/* ev: tynt_ai_backoffice src/api/pipelineTest.ts (step1-remove-bg, step2-character-sheet, step3-layout-refine, task status); scripts/seed_content_manager.py (menu pipeline-test) */}
- SSE와 자산별 개별 폴링으로 나뉘어 있던 상태 조회를 폴링으로 일원화하고, 최대 50건 배치 조회 API(bulk-status)로 통합
- 50건을 넘는 요청은 요청 검증에서 422로 거절하고, 응답을 조회된 assets[]와 notFound[]로 나눠 일부 ID가 없어도 나머지 폴링을 이어 감. progress는 상태와 관계없이 0~100 값으로 항상 포함 {/* ev: tynt_ai_frontend_v2 BULK_API_BE_RESPONSE_EVALUATION.md (quotes tynt_ai_backend docs/api/BULK_STATUS_API_FE_RESPONSE.md) */}
- 권한 없는 ID도 notFound[]로 돌려줘 다른 사용자 자산의 존재 여부를 드러내지 않고, 단건 조회 API는 그대로 둬 여러 건을 보는 앨범·갤러리 화면만 bulk-status로 전환 {/* ev: tynt_ai_frontend_v2 BULK_API_FE_FEEDBACK.md (errors[] → notFound[], 하위호환, Context 기반 전략); BULK_API_BE_RESPONSE_EVALUATION.md (Hybrid 전략 동의) */}

Aura는 스타일 변경·영상 생성·실험실 콘텐츠 생성에 쓰는 서비스 내 크레딧이다. 비용 조회 방식이 둘로 갈려, 스타일 변경·영상 생성은 요율 API에 웹 코드의 기본 요율을 폴백으로 붙여 썼고 실험실은 서비스 상세의 비용 필드를 따로 읽었다. 기본 요율이 프론트 코드에 있어 비용을 바꾸면 프론트 배포가 필요할 수 있었다. {/* ev: tynt_ai_frontend_v2 docs/BE_QUESTION_AURA_RATES.md (현재 구조, 문제점) */}

- 모든 비용을 aura_usage_rates 테이블의 기능 유형별 단위 비용으로 모으고, 실험실 서비스는 서비스마다 요율 행을 참조해 가격을 따로 책정. 이름·설명은 Accept-Language 헤더에 맞춰 응답 {/* ev: tynt_ai_frontend_v2 docs/BE_RESPONSE_AURA_RATES.md (질문 1·2) */}

{/* ev: tynt_ai_backoffice docs/coupon-conventions.md (c435f43cc); coupon commits 57/67 owner (traceability) */}

프로모션마다 대상과 지급 시점이 다르다. 특정 사용자 한 명에게 주는 보상, 전체 사용자에게 여는 할인, 코드를 입력한 사람만 받는 쿠폰, 가입·첫 결제 때 자동으로 주는 쿠폰을 모두 배포 없이 운영에서 만들 수 있어야 했다. {/* ev: tynt_ai_backoffice docs/coupon-conventions.md 1.2 (발급 방식별 강제 이유); sections (백오피스에서 설정, 배포 없이) */}

- 쿠폰 발급 4종(코드·직접·일괄·자동)과 자동 지급 조건(가입·첫 결제)을 백오피스에서 설정
- 발급 방식에 따라 쿠폰 타입을 고정. 직접 지급은 1인 전용, 일괄·자동 지급은 공용으로 강제하고 코드형만 공용·1인 전용을 고르게 했으며, 발급 방식은 생성 뒤 바꿀 수 없음 {/* ev: tynt_ai_backoffice docs/coupon-conventions.md 1.1, 1.2 */}
- 쿠폰은 할인율별로 등록한 패키지 가격에 연결해 적용 가격을 하나 이상 지정하고, 결제 채널(전체·앱 인앱 결제 전용)로 사용처를 제한 {/* ev: tynt_ai_backoffice docs/coupon-conventions.md 1.1, 4.1, 4.2; b8d7473a0 (package prices page) */}
