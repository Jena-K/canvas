Genvas는 웹툰 작가가 AI로 캐릭터와 작화를 생성하고 협업하는 SaaS다. 작가는 스토리보드에서 단계별로 이미지를 생성하고, 자기 그림으로 캐릭터를 학습시키거나 테마를 골라 이미지·영상을 만든다. 시스템은 핵심 백엔드·인증·검색·결제·운영 어드민 등 8개 서비스로 나뉘고, 생성 요청은 Celery 워커 체인을 거쳐 외부 생성 모델로 전달된다. {/* ev: genvas/record.md (product identity, 8 services); genvas-renewal-api record F7 (theme image/video); sections task 3 (character training) */}

Django로 만든 1세대 백엔드(genvas-api)를 대체하는 FastAPI 백엔드 genvas-renewal-api의 주 개발자로 커밋 대부분을 작성했다. 생성 파이프라인, 크레딧·결제·구독, 인증, 검색 이전, 모듈 구조 재편이 이 저장소에서 한 일이다. 운영 어드민 두 저장소(admin, genvas-admin)는 혼자 개발했고, Go에서 Python으로 옮긴 인증 서비스(genvas-renewal-auth)에는 PostgreSQL 모델과 이메일 로그인 서비스를 더했다. 사내 이미지 합성 엔진 Simba에서는 학습·생성 큐 분리와 중앙 오케스트레이터 구조 전환에 참여했다. {/* ev: traceability.md owner shares (renewal-api 631/748, admin 18/18, genvas-admin 10/10, simba participation user-confirmed 2026-10-22); genvas-renewal-auth 3ef8351ae, c6db51d22 (owner 10/30); genvas-renewal-api record.md (genvas-api successor) */}

## AI 생성 파이프라인

### 다단계 생성(마네킹→캐릭터→업스케일→선화→채색→얼굴보정)을 비동기 워커 체인으로 단계 격리

생성 한 건은 마네킹부터 얼굴보정까지 여섯 단계를 차례로 거친다. 최종 상태만 덮어쓰는 구조라 어느 단계에서 왜 실패했는지 남지 않았다. {/* ev: assumed rationale (recommended, no evidence; user-approved 2026-10-22) */}

- BE·Worker 간 연동 호출을 6→2단계로 간소화하고 서버 역할별 책임을 분리해 중복 로직·불필요한 호출 제거
- 태스크 단위 로그와 상태 변경 이력을 쌓는 이벤트 기반 상태 추적으로 재구축 {/* ev: assumed rationale (recommended, no evidence; user-approved 2026-10-22); celery_task_logs = genvas-renewal-api app/core/celery/adapter.py */}
- 체인마다 워크플로 ID(UUID v7) 하나를 발급하고, 단계 번호·큐·태스크·인자를 celery_task_logs에 생성물(service_table·service_id) 기준 색인으로 저장해 레거시 v2 생성물과 v5 에셋을 한 테이블에서 조회 {/* ev: genvas-renewal-api app/core/celery/adapter.py send_tasks, app/core/celery/models/celery_task_log.py, app/core/celery/services/unified_celery_task_log_service.py (4e8cb9fe2) */}

## 결제·크레딧

### 결제 시도와 완료가 한 테이블에 섞여 감사 추적이 어렵던 구조를 가변 결제 시도와 불변 완료 기록으로 분리

{/* ev: genvas-renewal-api F5 (1cce58169, b27bf9385, fe3d5df27, docs/TRANSACTION_ORDERING.md) */}

- payment_transactions는 대기·완료·실패·취소를 모두 담는 가변 테이블로 두고, 결제사·결제사 주문 ID·상품·통화·구독 등 8개 컬럼 추가 {/* ev: PAYMENT_EVENT_SOURCING_COMPLETE_2025_12_11.md §1, app/api/v5/payments/models/payment_transaction.py; 1cce58169 */}
- payment_records는 완료 건만 시도당 1건(payment_transaction_id 고유)으로 남기고, 상품명 스냅샷과 완료 시각을 담은 불변 기록으로 재구성 {/* ev: PAYMENT_EVENT_SOURCING_COMPLETE_2025_12_11.md §1; 1cce58169 */}

### 구독 해지를 결제사 쪽 자동 갱신 중단까지 연동하고, 연속 갱신 실패를 이력으로 판정

## 인증·계정

### 계정과 로그인 수단을 분리해 한 계정에 이메일·OAuth 로그인을 함께 연결

기존 인증 서버(genvas-auth)는 Go와 DynamoDB 위에서 Kakao·Line OAuth 로그인만 처리했다. 리뉴얼에서는 이메일 가입을 새로 받으면서, 한 사람이 이메일과 OAuth로 각각 들어와도 같은 계정으로 이어져야 했다. {/* ev: genvas-auth/record.md (system context only, owner 0 commits); genvas-renewal-auth/record.md (native auth added); genvas-renewal-api app/api/v5/auth/models/account.py v2.0.0 ("single account with multiple authentication methods") */}

- Python으로 옮긴 인증 서비스(genvas-renewal-auth)에 PostgreSQL 모델·서비스 계층을 추가해 DynamoDB 레거시와 함께 운용하고, 이메일 로그인은 NativeAuthService로 분리 {/* ev: genvas-renewal-auth 3ef8351ae (postgresql_models, postgresql_service), c6db51d22 (native_auth_service) */}
- v5에서는 계정 테이블(accounts)의 로그인 방식 컬럼을 없애고, 자격 증명을 native_credentials(계정당 1개)와 oauth_credentials(제공자별)로 분리 {/* ev: genvas-renewal-api app/api/v5/auth/models/account.py v2.0.0, native_credential.py (account_id unique), oauth_credential.py; 7170f73ea */}
